# GA4 server-side Purchase
Objective: Send GA4 Purchase from confirmed payments using Measurement Protocol, alongside existing browser GA4 and Meta CAPI.
Branch: `feat/ga4-server-purchase` (base `03680346`); delivery: single-pr (user-approved size exception); runner: backend pytest and portal Vitest/checks.

## Specs

- **S1 — GA4 server-side purchase.** User: "Tenemos que empezar a investigar como implementar ga4 server side, asi como tenemos CAPI, pero de google"; "Tenemos que empezar esta implementacion"; "tenemos que seguir lo que se hace con capi, pero con ga4". Scope: tenant-scoped GA4 Purchase for the same eligible confirmed-payment events as Meta CAPI. Acceptance: encrypted tenant API secret, browser GA identifiers captured at checkout, persisted on payments, and server request with payment ID as transaction ID. Keep the existing browser GA4 Purchase as a fallback and align its transaction ID for web-stream deduplication. Checks: focused Python/TypeScript tests, backend/portal checks, no real Google send without credentials.
- **S2 — No server begin_checkout.** User: "si begin checkout no tiene sentido, no lo agreguemos". Scope: do not add GA4 server-side `begin_checkout`; S4 now authorizes browser checkout-start tracking at the real user action. Acceptance: no new server-side `begin_checkout` emission. Checks: diff inspection and regression tests around purchase paths.
- **S3 — Return-time purchase confirmation.** User: "claro, pero esa ruta deberia tambien enviar evento no?"; "bueno modificalo". Scope: send the existing server-side Purchase notifications when the return-time SimpleFI reconciliation confirms a paid ticket. Acceptance: GA4 and Meta CAPI use the same committed approval transition; repeated confirmation or a later webhook does not schedule another Purchase; notification failures do not undo approval. Preserve release response and fulfillment behavior. Checks: isolated backend endpoint/approval regression tests, including return followed by webhook and the reverse order; no live provider sends.
- **S4 — Browser Purchase journey.** User: "Session start - View product - Add to cart - Begin checkout - Purchase"; "como q no, tenes que hacerlo, para que me decis hay que cambiar esto". Scope: complete the real browser ecommerce events in application and open/direct checkout so the standard Purchase journey can observe them. Acceptance: catalog view produces `view_item`, positive explicit ticket selection produces `add_to_cart`, valid checkout submission produces `begin_checkout` with selected items before purchase/provider submission; no artificial session/shipping/payment events, no emissions for preview, restoration, removals, invalid submissions or mere rerenders; preserve confirmed server Purchase and existing selection/payment behavior. Checks: RED/GREEN Vitest regressions at helpers/provider/submit/selection boundaries, portal suite and type/lint checks. No real analytics requests during tests.

- **S5 — Verified Portal payment return.** User: "Purchase journey sigue sin contra igualmente, pero tambien es rara la interaccion al volver de thank you page, que te muestra ese mensaje como si fuese un error, y te redirije a passes"; accepted proposal: "¿Corregimos el retorno para verificar el pago desde thank-you, mantenerte ahí y dejar “Ver mis pases” como acción explícita, sin ese error ni redirección automática?"; authorization: "si dale". Scope: verify the signed-in Portal buyer's own returned payment through a non-cancelling provider status check, reuse committed approval/fulfillment/Purchase idempotency, and keep the thank-you visible with explicit passes navigation. Present already-completed Portal checkout as success rather than error/forced navigation while retaining duplicate-payment guards. Never trust unsigned URL order data as approval; preserve tenant/owner boundaries and direct/external return behavior. Checks: RED/GREEN owned confirmation API, provider failures/pending/replays and authorization regressions; Portal return UI/checkout tests; generated clients, types/lint; independent security/ordering verification. GA report population remains unproven and separate.
